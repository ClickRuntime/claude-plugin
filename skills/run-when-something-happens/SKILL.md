---
name: run-when-something-happens
description: Run work when an outside event arrives, such as a form submitted, a payment received, a new GitHub issue, a Shopify order, a calendar booking, or any webhook. Use when the person says "when X happens", "whenever someone…", or asks for a webhook endpoint, and wants the arrival handled automatically.
---

Explicit instructions from the person override this skill. If they ask for something different from these steps, follow them, as long as it stays within the safety rules below.

## Decide first

- Use this skill when another service can send an HTTP request (a webhook) when something happens. If the service cannot send webhooks, offer a schedule that polls it instead (`run-on-a-schedule`).
- Pick the pattern:
  - `incoming`: each arrival runs the script right away (`@on_event`).
  - `remember_then_schedule`: arrivals are only stored in state (`@on_event`), and a scheduled `@on_trigger` run acts later, for example a daily digest of new sign-ups.

## Steps

1. Restate the outcome. Ask only for what is missing: which service sends the event, which event, and what should happen. Ask for a sample payload if the person has one; otherwise look up the sender's webhook docs as in [senders.md](references/senders.md) and read only fields they document. Do not invent payload fields. When the fields depend on the person's own setup (a form's questions, custom fields, a sheet's columns) and the sender has an API, offer to look them up with `run_setup_script` (`purpose: "discover"`), or let the person tell you the names, as in Looking things up and one-time setup in `write-and-fix-a-script`. Map each field to its destination by those names, and say which ones you could not match. If the script will use outside services (Google, Slack, any connected app or saved key), choose the accounts with the person now, as in Choosing accounts in `connect-a-service`, in the same message.
2. Write the script against [the runtime reference](../write-and-fix-a-script/references/runtime.md), starting from a matching template in [recipes.md](../write-and-fix-a-script/references/recipes.md) when one fits. Read the body with `event.json` and use `event.event_id` to avoid acting twice on a retried delivery.
3. If the sender signs requests, pass `signature` to `save_draft` so the platform checks every delivery before the script runs: `provider` (`stripe`, `github`, `shopify`, `typeform`, `standard_webhooks`, or `hmac_sha256` for any other sender that signs the raw body with HMAC-SHA256, with its `header`, `encoding`, and `prefix`), `secret_name`, and `require: true`. Add the same name as a secret need (a script that verifies itself reads it with `credentials.secret`); the person saves the value in the ClickRuntime dashboard, never in chat. For a scheme the platform cannot check (such as Calendly), verify with `verify.*` in the script instead. See senders.md. For an automation that must not act twice, pass `retry: {"max_attempts": 1}`; the default retries platform errors and timeouts up to 3 attempts.
4. Call `save_draft` with `pattern: "incoming"` (or `"remember_then_schedule"` with a `schedule`), `name`, `summary`, `script`, and `setup_needs` (each connection with the account `name` the person chose in step 1). The trigger link is created with the draft; events that arrive before the automation is live are stored, not run.
5. Call `get_setup_status`. Its result has the trigger link (`trigger.url`) and anything still missing. Give the trigger link exactly as returned and tell the person where to paste it in the sending service, which events to choose, and to use JSON, from the sender's current docs (see senders.md). Follow The setup loop in `connect-a-service` for missing connections or secrets: put every step, each with its link, in the same reply, and wait until they say they have finished.
   - Register the webhook yourself when the automation already has an API key or connection for the sending service: one it needs for discovery or other setup, or one the person offers to save. If the sender's API can create webhooks, do it with `run_setup_script` (`purpose: "setup"`) once the key is saved: point it at the trigger link, choose the events, and set a signing secret if the API allows. Then tell the person it is done instead of giving them dashboard steps. If the API cannot do it or the call fails, give the manual steps from the sender's docs. Do not ask for a key only to register a webhook; when data arrives by webhook, the script does not need the sender's key.
6. Before deploying, you can call `send_test_event` with a sample body: on a draft the event is stored without running. Compare its fields with what the script reads (use `get_latest_event` for events the sender delivers) and fix the script with `update_draft` if they differ.
7. When setup is ready, deploy it: `update_draft` with `deploy: true`. If the result says it is still deploying, call `wait_for_deploy`. Say it is live only when the result shows the deploy succeeded. Then tell the person it is set up, that it runs when the next event arrives at its trigger address, and what one event causes outside ClickRuntime (emails sent, rows added), and offer to send a test event now. Wait for the answer.
8. If they say yes, test it live: call `send_test_event` with a realistic sample body; on a live automation it runs the script and returns the run. Once real events arrive, `replay_event` with an `event_id` from `list_incoming_events` runs one again. If a run fails, fix and redeploy with `propose_change` and `deploy: true`, then test again, as in Deploy, test, fix in `get-started`, until a run succeeds. Then report what the test did and any fixes you made.

## Without cards

If no card appears, describe the result in a sentence or two. A `confirm_url` (from `prepare_confirmation`, used for deleting) goes to the person exactly as returned; they confirm or cancel on that ClickRuntime page. After they say they have, call `get_confirmation_status` with the `confirmation_ref` and report what it shows. See `get-started` for details.

## Refuse or narrow

Decline, with a short reason, when the request is to run malware, stealth monitoring of a person, or credential theft; to bypass another service's access controls or rate limits; to move money, place a trade, or complete a purchase; or to collect health, government, or payment-card data. Reacting to a payment by sending a receipt or adding a row is fine; issuing refunds, payouts, or transfers is not. Never bring up run or AI limits during setup. Only when a tool says a limit was reached, say so as a fact and give the link from that tool's message exactly as returned, with no plan names, prices or advice to change plan. Monthly runs used up: automations can still be turned on or resumed and start when the period resets, but running one now waits until then. AI tokens used up: say so and offer a version without AI.

Never ask the person to paste an API key, token, password, or one-time code. Never put a secret in a tool argument. If a saved key is missing, give them its link to the ClickRuntime dashboard. If they paste a secret anyway, tell them to revoke it and create a new one in the ClickRuntime dashboard, and do not repeat the secret.
